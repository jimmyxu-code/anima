# 四层技术架构 · 整合版

> 2026-08-24。用途：把 L1 助手级、L2 混合级、L3 原生级、L4 数字生命级的**技术边界、共享资产与演进接口**集中到一处。
> 
> 本文只保留技术内容：不包含用户画像、商业定位、人格话术、融资或价值判断。它是阅读四层的工程入口，不取代当前运行态：L1 以 `docs/01-总纲/交接总档-2026-08-23.md` 为准；L2-L4 仍以 `四层架构-总纲.md`、`L3-L4-原生与数字生命.md`、`L4-生命原理与统一架构.md` 为构想基准。

## 1. 阅读口径

| 标记 | 含义 |
|---|---|
| **现役** | 当前项目中运行或已由离线回归覆盖的实现 |
| **验证** | 已在隔离验证机或原型出现过，但不是当前主运行路径 |
| **构想** | 已定义边界和接口方向，尚未进入实现或验收 |

四层不是四套彼此复制的系统。技术关系是：L1 验证器官与协议，L2 改变 Windows 上的宿主与交互表面，L3 将宿主替换为 AI 原生运行时，L4 在该运行时上增加可塑状态、选择机制和长期闭环。

```text
L1 Windows 助手运行时
  └─ 可迁移资产：任务/事件、记忆、技能、权限与证据、消息契约
       ↓
L2 Windows 增强宿主与安装/回滚层
       ↓
L3 原生引导、AI 运行时与网络化交互壳
       ↓
L4 持久状态、学习选择、世界模型与多设备调度
```

## 2. 四层技术矩阵

| 层级 | 宿主与部署边界 | 核心运行时 | 主要抽象 | 状态 |
|---|---|---|---|---|
| **L1 助手级** | 现有 Windows 桌面进程 | 全双工语音、插件微内核、任务会话、exec-native | 对话、工具调用、任务、GUI 动作 | **现役** |
| **L2 混合级** | Windows 仍保留为应用/驱动宿主；安装、回滚和 Shell 由增强层管理 | 复用 L1 runtime 与能力插件 | Agent Space、系统能力、受控 Windows 表面 | **验证/后续** |
| **L3 原生级** | 可烧录 Linux/极简 AI 宿主；Windows 仅作为可选兼容后端 | 硬件抽象、模型调度、统一总线、网络化 UI | 活动、语义对象、能力、模型服务 | **构想** |
| **L4 数字生命级** | L3 或等价宿主上的持久节点与设备池 | 全局工作空间、记忆/技能可塑层、评测选择层、世界模型 | 身份状态、目标、经验、器官、设备 | **构想** |

## 3. L1 · 助手级（现役技术基线）

### 3.1 运行流

```text
输入设备
  → doubao_duplex 全双工 S2S
     ├─ 语音层函数调用：look_screen / run_task / task_status / recall_memory 等
     └─ ASR 终稿 → chat_brain 分类
                        → TaskSession
                        → plugins/exec_native 执行循环
                           ├─ 只读 delegate（受限并发）
                           └─ gui_agent 前台执行
                                ├─ gui_provider / gui_providers
                                ├─ UIA / DOM / 视觉定位
                                └─ 真实输入与用户接管检测

任务状态、确认、证据、进度 → task_overlay / 事件与会话账本
播报 → 本地渲染 + say_hello 确定性通道
```

### 3.2 现役组件与硬契约

| 范围 | 当前组件 | 技术契约 |
|---|---|---|
| 语音与事件 | `doubao_duplex.py`、`plugins/voice_fc.py` | 双工事件需先 probe；函数回传使用已验证的 `role=tool` 形态；不可见工作登记到 overlay |
| 编排 | `kernel.py`、`plugins/`、`chat_brain.py` | 能力经插件注册；路由只判不答；聊天链路与执行链路隔离 |
| 任务 | `task_session.py`、`plugins/exec_native.py` | `task_id`、revision、executor epoch、cancel token、检查点、已完成步骤和证据共同构成租约 |
| 权限与证据 | `confirm_policy.py`、`execution_authority.py`、执行插件 | 高危操作绑定一次性确认；旧 epoch 不能提交状态/副作用；模型文字不是完成证据 |
| GUI | `gui_agent.py`、`gui_provider.py`、`gui_providers/` | 模型动作先规范化；未知或混合 GUI/CLI/API 批次 fail-closed；用户真实输入优先接管 |
| 记忆与表达 | `plugins/memory.py`、`plugins/identity.py`、`plugins/expression.py` | 人格、记忆和任务表达各自有单一入口；运行时数据不由模型直接改写 |

L1 证明的是跨层最小可行器官：感知、表达、工具、任务账本、权限门、记忆和事件记录可以在真实桌面环境闭环。L1 的当前运行架构以交接总档为准；已退役的 dsh 执行链不属于该基线。

## 4. L2 · 混合级（Windows 增强宿主）

L2 不替换 Windows 内核或现有应用。它增加一个可安装、可回滚的智能体宿主层，负责把 L1 已验证的 runtime 与能力暴露为系统级交互表面。

### 4.1 技术组成

| 子系统 | 职责 | 与 L1 的关系 |
|---|---|---|
| Agent Space / Shell 表面 | 提供全屏或常驻的智能体交互画布 | 复用 L1 对话、任务和 overlay 事件；不另建第二套会话 |
| Windows 能力适配 | UIA、GUI、DOM、系统命令、文件与设备能力 | 继续由 L1 能力插件和权限门统一调用 |
| 安装与配置层 | bundle、安装脚本、服务/配置部署、版本记录 | 必须可重复执行、可诊断、可回滚 |
| Shell 切换与 watchdog | 可选地替换用户态 Shell 并提供恢复路径 | 与 L1 runtime 解耦；故障时必须恢复到标准 Windows 表面 |
| 资源与电源策略 | 前后台优先级、合盖/熄屏策略、健康检查 | 不得阻塞用户交互，也不得扩大执行权限 |

### 4.2 工程边界

- Windows 内核、驱动与既有应用仍是宿主能力；L2 不自行重写它们。
- 安装、减脂和 Shell 改动属于系统级变更，必须有验证机、回滚路径和可观察日志，不能混入 L1 日常对话/执行热路径。
- L2 只改变 UI 和宿主编排，不改变 L1 的任务租约、确认、证据和用户接管不变量。

## 5. L3 · 原生级（AI 原生运行时）

L3 的目标是把 L2 的“Windows 增强层”替换为自有宿主。当前仅定义技术方向，未进入代码实施。

### 5.1 分层运行时

| 层 | 计划组件 | 责任边界 |
|---|---|---|
| 硬件抽象/固件层 | 极简 Linux、设备枚举、网卡、GPU、音频、USB HID、摄像头驱动 | 仅提供稳定设备能力与资源事实，不承载任务语义 |
| AI 运行时/内核态 | 模型加载、Token/KV cache 预算、会话调度、消息总线、能力注册 | 管理推理与任务资源；保持任务、权限和事件协议可审计 |
| 网络化 UI/用户态 | 全屏画布、实时渲染、活动布局 | 不依赖桌面、任务栏或文件管理器；界面由运行时状态驱动 |

### 5.2 L3 的四个替换抽象

| 传统抽象 | L3 抽象 | 需要保留的底层事实 |
|---|---|---|
| 窗口 | 活动（activity）及其状态、资源和可恢复检查点 | 显示设备、输入焦点和渲染表面 |
| 文件路径 | 语义对象与可检索元数据 | 实际存储位置、访问控制、版本与删除语义 |
| 应用 | 能力/工具/远程服务 | 协议、凭据、权限、失败与回滚 |
| 单一模型 | 分层模型服务 | 资源预算、输入输出类型、可观测日志 |

### 5.3 孢子引导与部署模型

最小镜像由极简内核、初始 Ramfs、硬件能力图谱 schema 和启动调度器组成。启动过程应是：设备枚举 → 写入硬件事实 → 选择驱动与模型部署 → 计算内存/缓存预算 → 生成渲染与输入参数。模型、驱动、UI 和网络服务均是按设备事实部署的模块，而非写死的机器型号分支。

仅保留三类确定性约束：能耗预算、交互延迟阈值、记忆压缩/保留策略。其余部署策略应由探测结果和评测数据决定。冷门硬件、专有加密狗或无网络替代的本地客户端必须有明确“不支持”边界。

## 6. L4 · 数字生命级（持久、自适应运行时）

L4 不等于训练一个新基础模型。它在冻结的基础模型之外，增加长期状态、可塑资产和选择机制；基础模型与权限规则属于不可自改的核心。

### 6.1 三平面架构

| 平面 | 资产 | 变更规则 |
|---|---|---|
| 基因/核心平面 | 基础模型、核心提示、权限门、身份根、协议版本 | 版本化发布；不允许运行时自行覆盖 |
| 突触/可塑平面 | 记忆、技能、工作流、适配器、局部 LoRA、设备配置 | 可新增或更新，但每项必须带来源、范围、回滚和评测记录 |
| 选择/结晶平面 | 评测集、指标、沙箱、睡眠整理、归档/淘汰策略 | 决定可塑资产是否保留、升格、压缩或撤回 |

### 6.2 统一工作空间与器官联邦

L4 的统一性来自单一、类型化的全局工作空间，而不是把 ASR、视觉、LLM、TTS 合并成一个模型。各器官通过消息协议写入观测、任务、预测、动作结果和健康状态：

```text
感知器（音频 / 视觉 / 设备指标）
          ↘
        全局工作空间 / 事件账本
          ↙               ↘
规划与语言            记忆、技能、评测与世界模型
          ↘               ↙
        能力执行器 / 设备调度 / 结果证据
```

权限门相当于不可绕过的免疫层；任务租约、取消令牌和完成证据必须贯穿工作空间与执行器。任何自生成技能、工作流或模型适配器都只能进入可塑平面，不能直接改变核心平面。

### 6.3 近端技术切片

- **世界模型 v0**：以动作—状态—结果事件构建状态转移表；先作为预测/验证器，不直接授权动作。
- **睡眠/结晶**：定期压缩低频记忆、归档未使用技能、把通过评测的高频工作流升格为稳定能力。
- **感受器萌发**：由重复的信息缺口产出设备需求与集成规格；设备接入仍遵循权限、驱动、校准和验收流程。
- **设备池**：将多个设备抽象成带能力、负载、能耗和健康状态的执行节点；跨设备任务仍使用同一任务账本与取消/证据协议。

这些都是构想接口，不代表已获真实运行验证。

## 7. 跨层不变量与迁移包

| 资产/协议 | L1 当前形态 | 向上迁移要求 |
|---|---|---|
| 任务与执行租约 | `task_id`、revision、epoch、cancel token、checkpoint、completed steps | 字段语义不变，存储后端可替换；旧执行器永远不能提交新状态 |
| 权限与完成证据 | 确认绑定、动作门、证据分级 | 不随 UI、OS 或模型替换而降级；自动生成的计划也必须经过同一门 |
| 事件与消息 | 双工事件、插件调用、任务/overlay 状态 | 采用版本化类型与 append-only 记录；协议假设先以 probe 验证 |
| 记忆与技能 | 插件管理的文本/结构化数据与运行时文件 | 增加 schema、来源、评测、回滚和生命周期；不能让模型直接覆写根状态 |
| 感知与执行能力 | UIA、DOM、GUI、屏幕、音频、网络工具 | 统一为能力描述、输入输出类型、风险级别和健康状态 |
| 硬件配置 | Windows/设备 API 暴露的事实 | L3 后成为硬件能力图谱；仅记录观测到的事实，不把策略写成机器专用分支 |

建议把上述内容打包为可迁移的“runtime state + asset bundle + protocol version”，而不是复制某一层的进程、UI 或供应商实现。

## 8. 分层进入条件

| 目标层 | 进入前需要的技术证据 |
|---|---|
| L2 系统级增强 | 验证机安装/升级/回滚可重复；Shell/watchdog 故障可恢复；L1 全部安全不变量在新宿主不变；不干扰用户日常桌面 |
| L3 原生宿主 | 备用设备；最小镜像可启动；硬件枚举和能力图谱可复现；模型部署与资源预算有可观测数据；网络/本地能力均有故障边界 |
| L4 可塑闭环 | 事件账本可审计；技能/记忆有 sandbox、评测、版本和回滚；核心平面不可自改；任何自主/跨设备动作仍受同一权限、租约和证据链约束 |
